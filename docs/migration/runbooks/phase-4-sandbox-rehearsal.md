# Phase 4: sandbox rehearsal

**Classification:** sandbox only.
- Every change is made to **sandbox-namespaced resources inside the existing account `800960611664`**.
- No production AC resource or S4R resource is changed.
- The freeze (#2) stays in place.
- The imported `deploy.sh` scripts are never run.

Issue: #34.

**Goal:** before anything is imported in production (Phase 5), prove on disposable sandbox copies that:
- every Phase 5 resource type can be imported into AC CDK without being changed or replaced
- the shared S4R role is never managed by AC
- rollback and recovery work as documented

Runtime behaviour is not changed or improved in this phase.

**Decision (2026-10-07):** no separate AWS account is created. The sandbox lives in the production account, so isolation is
enforced by naming, a strict allowlist, the production and S4R denylists, and IAM. PLAN.md records the decision.

## 1. Naming convention

| Rule | Detail |
|---|---|
| **Suffix** | Every sandbox physical name is the production name with `-sbx` appended: `whichpart-api` → `whichpart-api-sbx`. Where the production name ends in the account ID, `-sbx` goes before it: `whichpart-web-sbx-800960611664` |
| **Sandbox-only resources** | Resources with no production counterpart end in `-sbx` too: `ac-operator-sbx`, `iam-t2-role-sbx` |
| **CDK toolkit** | Qualifier `acsbx` (qualifiers allow no hyphen), stack `ApplianceClinicSandboxToolkit`. It is separate from the S4R `CDKToolkit` (`hnb659fds`) and from the Phase 5 production toolkit (`acclinic`) |
| **Stacks** | `AcDataStack-sbx`, `AcRuntimeStack-sbx`, `AcIamExperiments-sbx`, and the stand-in S4R stack `SparesSite-sbx` |
| **Secrets** | Under the separate namespace `applianceclinic-sbx/`. This is outside `spares4repairs/*`, which the S4R server role can read (see [section 4](#4-what-the-runtime-code-forces)) |
| **Generated identifiers** | Function URL hosts, the HTTP API ID, Cognito IDs, secret ARN suffixes and backup ARNs are generated by AWS and cannot carry `-sbx`. Each is accepted only as a child of an allowlisted resource, is recorded on #34 when created, and is labelled a sandbox identifier |
| **Tag** | Every resource that supports tags carries `ac:sandbox=phase-4` |

## 3. Guard: allowlist and denylists

Every sandbox mutation must satisfy **both**:
1. the target is on the sandbox allowlist
2. the target is not on any denylist

| Layer | Mechanism |
|---|---|
| **Allowlist** | [`sandbox-allowlist.json`](../sandbox-allowlist.json): the exact physical names above. A generated identifier is accepted only when a describe call shows it belongs to an allowlisted parent (for example, the URL of an allowlisted function). It is recorded in `.migration-output/sandbox-generated.json` and on #34 |
| **Production AC denylist** | [`ac-production-denylist.json`](../ac-production-denylist.json), 83 entries from the Phase 0 inventory: every production AC function, Function URL host, log group, role, inline policy, table, backup, bucket, secret, ECR repository, rule, the CloudFront distribution, its function and certificate, plus the reserved Phase 5 names (`ApplianceClinicToolkit`, `acclinic`, `AcDataStack`, `AcRuntimeStack`, `AcAuthStack`) |
| **S4R denylist** | [`s4r-denylist.json`](../s4r-denylist.json), regenerated the same day as any sandbox mutation |

**Matching:**
- Allowlist and production AC entries are matched **exactly**, or by token boundary when a document is scanned. So `whichpart-api` never matches `whichpart-api-sbx`, and the reverse.
- S4R entries are matched exactly and by substring scan, as the existing checker does.

**Enforced in four places:**

| Where | Rule |
|---|---|
| **Sandbox guard** (`tools/migration`, next PR) | Before any sandbox command, the guard checks: <ul><li>the account is `800960611664` and the region is `eu-west-1`</li><li>the caller is the `ac-operator-sbx` role or an `acsbx` toolkit role</li><li>every mutated identifier passes the allowlist and both denylists</li></ul> Tests prove that production and S4R identifiers are refused. Only named commands can run, as in the existing backup and hotfix tools |
| **Change-set checker** (sandbox mode) | Every `PhysicalResourceId` and every ARN in the template must be allowlisted. The only exceptions are AWS-managed policy ARNs (`AWSLambdaBasicExecutionRole`) and service principals. Any non-sandbox resource with an `Add`, `Modify`, `Remove`, `Import` or replacement action fails |
| **IAM** | `ac-deny-production-sbx` is an explicit `Deny` on every ARN from both denylists, and on `secretsmanager:*` for `secret:spares4repairs/*`. It is attached to `ac-operator-sbx` and to the `acsbx` CloudFormation execution role. Their allow policies (`ac-operator-policy-sbx`, `ac-cfn-execution-sbx`) name only sandbox ARN patterns. `ac-cfn-execution-sbx` is also the permissions boundary every sandbox-created role must carry. The toolkit's execution policies are those two, never `AdministratorAccess`. The exact documents, the reviewed bootstrap template and the commands are in [`sandbox/approval-a/`](../sandbox/approval-a/README.md) |
| **Lambda configuration** | Before a sandbox function is first invoked, its environment is checked: every override in section 4 is set to a sandbox value, and no value contains a production or S4R identifier |

| All | `STAGE` | `dev` | `sbx` |

**Secret names the code builds itself (decision recorded on #35).**
- **The names.** `whichpart-api` and the diagnosis Lambda build three secret names from `STAGE` alone, with no override variable:
  `spares4repairs/<STAGE>/applianceclinic-{ai-config,openai,jev}`.
- **Decision.** No `spares4repairs/sbx/…` secret is created in this account. It would place sandbox material inside the
  `spares4repairs/*` namespace that the production S4R server role can read, which weakens the isolation boundary.
- **Import only.** The three secrets are rehearsed for import and ownership only, as dummy `applianceclinic-sbx/{ai-config,openai,jev}`.
- **Runtime reads deliberately not exercised.** Their runtime reads are not exercised in the shared-account sandbox. This is
  not a Phase 4 blocker: the phase proves ownership, import and recovery, and does not change runtime behaviour.
- **Runtime reads are blocked:**
  - Every sandbox role carries an explicit `Deny` on `secretsmanager:*` for `arn:aws:secretsmanager:eu-west-1:800960611664:secret:spares4repairs/*`, so any attempt is refused before it reaches a secret.
  - Sandbox endpoint checks never call a path that reads them: the admin AI-configuration routes, and any LLM-backed answer path.
  - The function logs of each check are scanned. Any attempt to read a `spares4repairs/` secret is a STOP.

**The reverse direction.** Production principals with broad grants can reach sandbox resources. For example, the S4R server role
reads `spares4repairs/*` and holds four `Resource: "*"` statements across the inventoried roles. The sandbox holds no production
data, and sandbox secret values are dummies, so this is accepted. Sandbox roles hold no grant on any production resource.

## 5. Rehearsals

Each rehearsal follows the same pattern:
1. Create the sandbox resource outside CloudFormation, with the production configuration and sandbox names.
2. Import it with an import-only change set.
3. Make an update that should change nothing, and confirm it changes nothing.

CloudFormation documents resource import for `AWS::IAM::RolePolicy`, `AWS::Lambda::Url`, `AWS::Lambda::Permission`,
`AWS::Events::Rule` and `AWS::ECR::Repository`, as checked in review. The rehearsal confirms each one in practice.

| Phase 5 step | Rehearsal on the sandbox copy |
|---|---|
| 5.1, 5.2 | ECR: import; repository policy and lifecycle unchanged; image digest preserved |
| 5.2 | Secrets: import with no value in any template or `cdk.out`. Each secret keeps its production consumption pattern: runtime-read secrets stay runtime reads, and only the plaintext bearer-token variables PLAN.md names become `{{resolve:secretsmanager:…}}` dynamic references |
| 5.3 | DynamoDB: import with the key, GSI `gsi_activity`, TTL, on-demand billing and PITR enabled declared exactly |
| 5.4 | S3: import the bucket and its OAC-shaped policy. The policy's `AWS:SourceArn` names a placeholder distribution, never `E1QD02IAJZPJLM` |
| 5.5 | IAM roles: import without inline policies (T3) |
| 5.6 | Inline policies: import as `CfnRolePolicy` (T4); remove with Retain (T5) |
| 5.7 | Lambda: zip import from the Phase 3 rebuilt zip, with CodeSha256 unchanged; image import by the sandbox ECR digest |
| 5.8 | Function URLs and permissions: import with the host unchanged; remove the URL with Retain and import it again, with the same host |
| 5.9 | EventBridge: import the rule and target, with schedule and input unchanged. The rule stays DISABLED; the import must not change that |
| 5.10 | Diagnosis copy: import the function **without** its role, referencing `SparesSite-sbx-ServerFunctionRole` unchanged. URL with RESPONSE_STREAM and CORS unchanged. Its `apigateway-invoke` permission (for `spares4repairs-sbx`) stays unmanaged |

### IAM experiments T1 to T7

PLAN.md refers to these experiments as defined in the original review, which is not in this repository. They are restated here
from PLAN.md's summary.

| Test | Question | Pass condition |
|---|---|---|
| **T1** (mandatory) | Does an unrelated update of `SparesSite-sbx` remove inline policies the stack does not manage from `SparesSite-sbx-ServerFunctionRole`? | The hand-added policies are unchanged after the update. This is PLAN.md's pass condition, unchanged |
| T1b (extra probe) | The same, when the update changes the role itself (a tag or description) | Records the behaviour. The result becomes a CDK rule, not a T1 failure. It is a Phase 5 STOP only if the production plan would make such an update to a role that carries unmanaged policies |
| T2 | What does declaring `Policies` on `AWS::IAM::Role` (`Role.Policies`) do to inline policies that are not declared? (`iam-t2-role-sbx`) | Records the behaviour. If undeclared policies are removed, that confirms the rule "never use `Role.Policies`" |
| T3 | Importing a role with no `Policies` property, then updating it | Its existing inline and managed policies are unchanged |
| T4 | Importing an existing inline policy as `AWS::IAM::RolePolicy` | `Import` actions only; document unchanged; drift detection clean |
| T5 | Removing an imported `RolePolicy` with `DeletionPolicy: Retain` | The policy stays on the role |
| T6 | Removing an imported role with Retain | The role and its policies stay |
| T7 | `AWSLambdaBasicExecutionRole` on an imported role, declared and then not declared in `ManagedPolicyArns` | Records whether an update detaches it. The finding becomes a CDK rule |

### Controls

| Control | Rehearsal |
|---|---|
| **Rollback with Retain** | Fail an update on purpose. The stack rolls back and no resource is deleted or replaced |
| **Stack policy** | Deny `Update:Replace` and `Update:Delete` on data resources, Function URLs, permissions and the diagnosis copy. A change set that replaces one is refused |
| **Termination protection** | On for every AC sandbox stack; deleting the stack is refused until it is turned off on purpose |
| **Change-set checker** | Run on every real change set, in import, update and sandbox modes. Its rules are finalised here. Each failure it should catch is shown failing, including a template that names a production AC or S4R identifier |
| **Deny-S4R execution role** | A sandbox AC template that tries to change `SparesSite-sbx-ServerFunctionRole` fails with AccessDenied. A template that names a production ARN fails at the checker and at IAM |
| **No `CDK::Metadata`** | Analytics reporting is off, so import-only change sets contain no Add action |

### Build and deploy path

The Phase 3 artefacts are deployed to the sandbox copies:
- both zips from `package_zips.py`
- both images built from `build/images/` and pushed to the `-sbx` ECR repositories

Checks:
- **Configuration:** compared with the Phase 0 baseline field by field. Expected differences are only names, ARNs, the section 4 overrides, dummy secret values and the DISABLED rules.
- **Permissions:** compared statement by statement, with production ARNs mapped to their sandbox names.
- **Endpoints:** checked only where no LLM, production data or S4R call is needed: routing status codes, auth rejections, error-path response shapes. They are called only at the generated sandbox URLs, from this environment.

### Recovery rehearsal

The rehearsal uses synthetic data only. The `-sbx` tables are seeded with generated items in the production schema; the
`-sbx` buckets with generated objects. Production backups (#6) hold customer conversations and are never restored, read or
copied.

| Step | Procedure | Recorded |
|---|---|---|
| DynamoDB on-demand backup | `CreateBackup` of `whichpart-*-sbx`, then `RestoreTableFromBackup` into `*-sbx-restored-backup` | Time to `AVAILABLE` and to `ACTIVE`; item count and key set equal; GSI, TTL and PITR on the restored table (restores carry neither TTL nor PITR) |
| DynamoDB PITR | Change items, then `RestoreTableToPointInTime` into `*-sbx-restored-pitr` | The restored table matches the chosen point |
| S3 from a backup copy | Copy into `applianceclinic-migration-backup-sbx-800960611664/<source-bucket>/<timestamp>/` (the Phase 0 layout), overwrite and delete some originals, restore from the copy | Object count and SHA-256 of every object equal; time taken |
| Switch back | How a restored table or bucket would be put into service | Recorded as a procedure only. No production restore is rehearsed |

The output is the recovery runbook, `phase-4-recovery.md`, merged before Phase 4 exits.

### Destroy and recreate

1. Every sandbox stack and resource is destroyed, by allowlisted name only. Retained resources are deleted explicitly. A deletion or replacement outside the allowlist is a STOP.
2. A READ-ONLY inventory of the production AC resources, compared with `compare:config` against the current approved baseline (the Phase 0 inventory plus the approved backup and admin-hotfix changes, see [approved changes](../phase-0-findings.md#approved-changes-since-the-baseline)), shows them unchanged.
3. The rehearsal is recreated from the repository and passes again.
4. Finally, the sandbox is destroyed, and the absence of every allowlisted name is confirmed.

## 7. STOP conditions

Stop, change nothing more, and report on #34 if any of these happens:

1. **Wrong account or region.** The caller account is not `800960611664`, or the region is not `eu-west-1`.
2. **Wrong caller.** A mutation would run as anything other than `ac-operator-sbx` or an `acsbx` toolkit role. The one exception is creating those roles themselves, at approval point A.
3. **Not on the allowlist.** A command, template or change set would mutate an identifier that is not on the sandbox allowlist, or not an accepted generated child of an allowlisted resource.
4. **On a denylist.**
   - Any mutated or referenced identifier matches the production AC denylist or the S4R denylist.
   - A template references any ARN in account `800960611664` that is not allowlisted. The only exceptions are AWS-managed policies and service principals.
5. **Deletion outside the sandbox.** A deletion or replacement is proposed for anything outside the allowlist, including through a change set.
6. **Unexpected change-set actions.** An import-mode change set contains anything other than `Import` actions, or an update-mode change set shows an unexpected `Replace` or `Remove`.
7. **Production values in a sandbox function.** A sandbox function's configuration would leave a section 4 override unset, or contain a production AC or S4R endpoint, name or ARN.
   A sandbox function's logs show an attempt to read a `spares4repairs/` secret.
8. **Production data, secrets or endpoints.** A step would need production data or production secret values, or would call a production AC or S4R endpoint.
9. **Forbidden scripts.** A step would run an imported `deploy.sh`, anything from `spares4repairs`, or the default `CDKToolkit`.
10. **Missing fact.** A fact can only be found in `spares4repairs`. Ask first.
11. **Failed rehearsal.** A rehearsal fails its pass condition, for example:
    - T1 finds an inline policy removed after an unrelated update.
    - A Function URL host changes on re-import.

    This is a Phase 5 blocker. It is recorded and turned into a rule before continuing.
12. **Budget.** The sandbox budget alarm fires.
13. **Production unhealthy.** Any S4R or production AC health check fails during the phase, whether or not it looks related.
